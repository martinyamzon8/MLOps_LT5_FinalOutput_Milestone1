PART 4: SLOT 3 — INDIVIDUAL Q&A CHEAT SHEET (4 TO 6 MINUTES)
================================================================================
The instructor will pick individual group members to answer. 
Here are the most likely questions and exact answers:

--------------------------------------------------------------------------------
Q1: "Where is your model stored and how does your FastAPI app load it?"
--------------------------------------------------------------------------------
A: "Our model is registered in the MLflow Model Registry under the name 
   'PAL_Passenger_Segmenter' with version tag 'v1.0.0'. When the FastAPI app boots up 
   (in `api/model_loader.py`), it reads the `MODEL_NAME` and `MODEL_VERSION` environment 
   variables. It first attempts to load from MLflow Registry (`models:/PAL_Passenger_Segmenter/v1.0.0`). 
   If MLflow is unreachable, it automatically falls back to our versioned artifact file 
   `models/pal_passenger_segmenter_v1.0.0.joblib`. It is never hardcoded to a fixed local path."

--------------------------------------------------------------------------------
Q2: "How did you calculate the confidence score for a KMeans clustering model?"
--------------------------------------------------------------------------------
A: "KMeans is non-probabilistic by default, so we compute the Euclidean distance from the 
   input point to all 3 cluster centroids using `model.transform(X)`. We then apply a 
   scaled softmax function over the negative distances: points right on a cluster centroid 
   approach 100% confidence, while points equidistant between clusters have lower confidence."

--------------------------------------------------------------------------------
Q3: "How do you ensure invalid data doesn't crash your serving endpoint?"
--------------------------------------------------------------------------------
A: "We use Pydantic models in `api/schemas.py` with field constraints (`ge=0` for lead time, 
   `ge=1` for passenger count, and `gt=0` for fare). FastAPI validates incoming requests against 
   this schema before reaching the inference logic. Invalid payloads immediately return 
   HTTP 422 Unprocessable Entity with error details, protecting our service from HTTP 500 crashes."

--------------------------------------------------------------------------------
Q4: "What statistical tests does Evidently use to detect drift in your report?"
--------------------------------------------------------------------------------
A: "For continuous numerical features like AverageFare and PurchaseLeadTime, Evidently applies 
   the Normalized Wasserstein Distance. For categorical features like Cabin and our discrete 
   cluster predictions, it uses the Jensen-Shannon Distance. Both tests compare incoming 
   production data distributions against our benchmark baseline."

--------------------------------------------------------------------------------
Q5: "If your monitoring report detects 40% drift in production, what do you do?"
--------------------------------------------------------------------------------
A: "As documented in our `reports/findings.md` playbook:
   1. Investigate the upstream data pipeline to rule out currency or data corruption issues.
   2. If the drift reflects true market changes (e.g. fare inflation), trigger our Airflow DAG 
      to ingest recent data and retrain the KMeans model.
   3. Log new metrics and register candidate `v1.1.0` in MLflow Registry.
   4. Once tests pass, update `MODEL_VERSION=v1.1.0` in Docker for a zero-downtime rolling update.
   5. Alert Revenue Management and Digital Marketing teams."

--------------------------------------------------------------------------------
Q6: "How did you test your code and what is your test coverage?"
--------------------------------------------------------------------------------
A: "We have 25 automated pytest tests covering:
   - Data validation (Pandera schema rejection)
   - Model quality (Silhouette score >= 0.45, Davies-Bouldin <= 1.0)
   - End-to-end DAG pipeline integration
   - FastAPI endpoint behavior (health, valid predict, 422 error handling)
   - Evidently drift generation
   Our test coverage is 81%, verified through `pytest --cov` and automated GitHub Actions CI."

PART 5: QUICK TROUBLESHOOTING & EMERGENCY COMMANDS
================================================================================

If Docker is not running or a container stopped:
1. Open VS Code terminal (`Ctrl + ` `).
2. Run:
     docker compose down
     docker compose up --build -d

If you want to run the FastAPI app directly without Docker:
1. In VS Code terminal, run:
     uv run uvicorn api.main:app --host 0.0.0.0 --port 8000
2. The API is immediately accessible at http://localhost:8000/docs

If you need to regenerate the Evidently drift report:
1. In VS Code terminal, run:
     uv run python monitoring/run_report.py
2. The report will be updated at `reports/evidently_report.html`.

If you need to run all tests to show the professor:
1. In VS Code terminal, run:
     uv run pytest tests/test_api.py tests/test_data_validation.py tests/test_model_quality.py tests/test_pipeline_integration.py tests/test_monitoring.py tests/test_train.py -v
2. To show test coverage:
     uv run --with pytest-cov pytest tests/test_api.py tests/test_data_validation.py tests/test_model_quality.py tests/test_pipeline_integration.py tests/test_monitoring.py tests/test_train.py --cov=api --cov=monitoring --cov=models --cov-report=term-missing
3. To show linting:
     uv run ruff check .
